# Operator Studio 项目讲解与任务分配（15 分钟）

配套页面：`operator-studio-module-workflow.html`

## 会前准备

- 浏览器打开配套页面，选择浅色主题。
- 确认顶部可以切换 `01 完整 Workflow` 到 `05 失败与恢复`。
- 告知成员：悬停模块可查看职责、输入输出、约束、可领任务和验收标准。
- 准备记录每个工作包的负责人、交付日期和依赖接口。

## 0:00-2:00｜目标与完整路径

页面操作：点击 `01 完整 Workflow`。

讲稿：

> 这个项目只有一套后端生产流程：当前 TUI 和未来 GUI 都通过相同 HTTP、SSE 和 DTO 进入业务编排，再完成基线、经验读取、候选生成、测试、Gate、状态持久化与经验沉淀。
>
> 图中的方框是模块，箭头是一次 Mission 的调用顺序。我们后续按模块边界并行开发，不允许在 TUI、HTTP 或执行器中另写一套 workflow。
>
> 今天需要确认三件事：每组负责哪个模块、向其他模块提供什么接口、用什么测试证明完成。

快速指图：

- 七个浅色区域对应七类职责边界；区域空白处 hover 看整体输入输出，节点 hover 看具体模块契约。
- `01-06`：从 TUI/GUI 到经验读取和 Candidate 写入。
- `07-12`：队列、通用执行工具、后端池和 Gate 决策。
- `13-14`：系统生成经验草稿，治理通过后沉淀到组织经验库。

## 2:00-4:00｜多端如何共用后端

页面操作：点击 `02 多端共用后端`。

讲稿：

> TUI 和 GUI 是平级客户端，共用统一后端接口。界面只负责交互和展示，不直接写状态，也不各自实现 Workflow。业务用例编排是唯一的用户操作入口。
>
> 因此 GUI 可以在底层硬件尚未完成时基于相同 DTO 和 Mock 独立开发。

## 4:00-7:00｜测试如何统一执行

页面操作：点击 `03 通用任务执行`。

讲稿：

> Candidate 写入后，由算子测试队列串行提交 Correctness 和 Benchmark。通用执行工具统一发现后端、准备执行包、提交、等待、取消和结果格式；C500 只是本地或远端后端之一。
>
> 自动推进读取测试结果，领域规则与 Gate 检查候选身份、正确性、性能回归和证据类型，再把决定投影到运行状态仓库。
>
> 执行器下一阶段要抽象为通用执行工具：统一查询本地或远端后端，传输内容寻址的执行包，预检依赖，并返回相同的任务状态、结果和错误。初期支持单入口文件及包内纯源码依赖，不支持任务运行时动态安装第三方依赖。

必须保持：

- 固定 Profile、shape、dtype 和测试矩阵不能被弱化。
- 仿真证据不能发布为真机证据。
- evidence、执行包摘要和实际 Candidate 必须一致。
- Queue 保持串行，并原子持久化唯一终态。

## 7:00-10:00｜经验何时读取和沉淀

页面操作：点击 `04 经验闭环`。

讲稿：

> 候选生成明确使用经验：轮次编排在 Candidate 生成前发起查询，查询服务筛选后返回冻结的 Experience Context，再由轮次编排把它放入候选生成请求。查询有三个时点：Mission 初始化、Baseline 完成后和领域失败或停滞时。Agent 不直接连接经验库。
>
> Correctness、Benchmark 或 Gate 得出可复用领域结论后，草稿生成器根据 Mission、Candidate 和真机执行证据生成正向或负向草稿。基础设施错误和仿真证据不生成经验草稿。
>
> 草稿随后进入独立治理：正向经验必须确认采纳落地，负向经验必须确认失败可复现。治理可以发布、合并、待补充或归档，只有合格资产进入正式经验库。

## 10:00-11:00｜失败与恢复

页面操作：点击 `05 失败与恢复`。

讲稿：

> 应用编排、Agent/Workspace、测试执行、经验治理和状态持久化异常统一进入错误契约。错误契约决定重试、人工处理或停止，并通过 HTTP 向 TUI/GUI 返回同一错误码、错误信封和恢复建议。Correctness、Benchmark、Gate 丢弃属于领域结果，不作为系统异常；只有可复现且具备领域价值的 Candidate 失败才进入负向经验草稿。

## 11:00-15:00｜任务分配

按下表现场填写负责人。一个人可以负责多个工作包，但每个工作包只能有一个最终负责人。

| 工作包 | 模块 | 第一阶段交付 | 验收重点 | 负责人 |
|---|---|---|---|---|
| A 界面与接口 | TUI、GUI、HTTP | 共享 DTO、SSE、错误展示和薄路由 | 两个界面不含 workflow；相同 DTO 语义 | 待填写 |
| B 流程与规则 | 业务用例、轮次、自动推进、Gate | 稳定 command/query、状态转移和 Gate 规则 | 所有成功/失败组合有确定结果 | 待填写 |
| C 候选环境 | Agent Runtime、Mission Workspace | Provider 端口、候选写入、Diff/checkpoint | Agent 不越界；候选摘要可验证 | 待填写 |
| D 测试执行 | Queue、通用执行工具、后端池 | 后端查询、执行包、依赖预检、本地/远端 C500 适配 | 行为一致；终态唯一；证据可追溯 | 待填写 |
| E 状态与错误 | State Repository、Error Contract | 并发写入、版本冲突、错误归一化和恢复 | 所有写入加锁；所有外部错误标准化 | 待填写 |
| F 经验闭环 | 查询与上下文、草稿生成、治理、正式仓储 | Experience Context、正负向草稿、分流决定和版本 | Agent 不直连库；非真机证据不生成草稿；仅合格资产入库 | 待填写 |

推荐依赖顺序：

1. B、D、E、F 先冻结公开数据结构和错误码。
2. C、D 使用 Mock 并行实现 Agent、Workspace 和执行后端。
3. A 最后接入稳定 API，不等待底层真实硬件即可开发。
4. 跨模块合并前运行 `npm run verify:local-c500-release`；无硬件改动补跑 `npm run verify:non-hardware-robustness`。

收尾话术：

> 会后每组提交一份简短模块契约：输入、输出、不变量、副作用、错误码和测试命令。改动如果改变公开契约，代码和 README 必须在同一个提交中更新。我们以图中的依赖方向和唯一生产流程作为合并边界。
