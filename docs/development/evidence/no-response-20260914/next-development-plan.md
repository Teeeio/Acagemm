# 诊断后的开发路径

本文件是 Root 的后续规划，不表示生产变更已实现或新的真实回归已执行。
沿既有方案 D 和 Production API → Client Runtime 路径推进。

1. **先补安全的运行诊断。** 在 Claude 客户端的 run record 旁保留有限的结构化信息：
   已解析事件类型计数、首次/末次输出时间、实际模型元数据首次出现时间、取消请求时间、
   物理 close 的退出码和信号。另在 Runtime 记录实际触发取消的分支及当时的预算/耗时。
   实施前冻结字段、缺省与同 run 身份绑定；诊断不能改变状态机、释放屏障或模型观测 DTO。
   不保存 thinking/prompt 正文，不用未经约束的 stderr 文本代替结构化原因。

2. **实现与独立测试按同一契约派发。** 重点场景是 init + thinking_tokens 后取消且无
   assistant、thinking-only assistant 的模型采集、无换行尾行、已观测模型后取消、
   取消请求等待超时但进程尚未退出，以及后续真实释放。验证诊断记录与状态真相一致，
   不能把取消请求当作已释放，也不能用配置或相邻 run 回填 actual model。
   只新增能验证这些契约的检查；现有覆盖继续复用，不因读取范围有限宣布全仓缺测。

3. **通过必要门禁后做真实验收。** 先核对新诊断在小范围真实两轮中的留存，再冻结代码、
   配置和驱动执行一个新的完整 N=20 批次。按既有模块与跨模块要求验证；原 83b91d6
   批次的失败、unknown 和所有原件保留。新批次也必须完整统计所有必需模型运行，
   出现 unknown 仍不能通过严格可比门槛，不追加第 21 次替换失败样本。

补诊断只能提高下一次故障的可解释性，不保证上游模型返回回答，也不构成扩大超时、
调整失败预算或放宽 N20 门槛的理由。若新证据明确指向具体实现问题，再对该问题制定修复。
