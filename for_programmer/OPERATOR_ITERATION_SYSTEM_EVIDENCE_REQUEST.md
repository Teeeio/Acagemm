# 给算子迭代系统项目 Agent 的信息采集任务

你当前位于算子迭代系统项目仓库中。该系统已经在算子优化比赛中取得第一名。请对该仓库进行一次只读信息采集，并生成可交付给另一个项目团队的事实证据包。

本任务只要求收集和整理算子迭代系统的真实信息，不要求你设计、重构或实现新系统。不要根据比赛结果美化项目状态，也不要把人工操作、脚本辅助或文档约定描述成已经产品化的能力。

## Current Understanding

以下是用户已经确认的事实。请用仓库证据逐项核对；找不到证据时保留为 `user-confirmed`，发现冲突时明确报告。

1. 核心 Agent 是 Codex。
2. 用户手动启动 Codex，并在需要时手动使用 `codex resume` 恢复对话。
3. 约束文档、经验文档、迭代历史、Gate 和测试相关机制主要保存在项目文件中。
4. 旧项目没有正式封装 Agent Runtime、统一事件协议或自动会话恢复。
5. 所谓“测试队列”主要是测试前清理环境、避免设备争用和缓存污染，然后逐个串行测试；不代表已经存在完整队列服务。
6. 人工介入通过用户直接与 Codex 对话完成，没有独立审批协议。
7. 没有明确的自动失败恢复；失败方案通常被放弃，并回退到可用历史版本。
8. Gate 用于表达测试是否满足要求以及流程是否继续。
9. 业务内容无需脱敏，但 API Key、Token、Cookie、认证头、登录态、证书等秘密必须移除。
10. 比赛第一证明整套工作方法有效，不代表每个脚本、目录和人工步骤都应原样保留。

## Collection Objective

采集结果必须让接收方在不依赖历史对话的情况下回答以下问题：

1. 一次真实的算子优化从任务输入到最终结果是怎样完成的？
2. Codex 实际如何启动、接收约束、读取经验、修改代码、获得测试结果和恢复上下文？
3. 测试前后如何清理环境、独占设备并保证严格串行？
4. benchmark、tracer、profiler 如何运行，输入输出是什么？
5. Gate 如何判断继续、采用、保留参考、放弃或回退？
6. 约束、经验和失败记录如何产生、查询、复用和追溯？
7. 代码版本、测试结果、Gate 结论和 Codex 对话如何关联？
8. 哪些措施有比赛或运行证据，哪些只是文档、约定或用户记忆？
9. 哪些行为是 Codex 特有的，哪些是与 Coding Agent 无关的算子优化领域行为？
10. 哪些关键信息在仓库中缺失、互相冲突或无法安全复现？

## Confirmed Constraints

1. 只读扫描。除指定输出目录外，不修改源码、配置、历史记录和已有文档。
2. 不安装或升级依赖，不提交 Git commit。
3. 未经用户明确授权，不运行真实 GPU/加速卡任务，不占用或清理共享设备，不调用付费模型或远端服务。
4. 可以运行不访问真实设备的离线解析、schema、Gate 和低成本单元测试。
5. 不得因文件名、注释、TODO 或设计文档存在，就认定相应功能真实运行过。
6. 不得把手动 `codex resume` 描述成自动会话恢复。
7. 不得把用户与 Codex 的直接对话描述成结构化审批系统。
8. 不得把串行脚本或人工纪律描述成完整测试队列。
9. 不得把放弃并回退描述成自动失败恢复。
10. 不得为了输出整齐而发明旧项目不存在的 ID、状态、协议或数据字段。
11. 可以记录一个手工步骤未来被封装时需要的输入、输出、状态和副作用，但必须明确标记为 `observed`、`inferred` 或 `unknown`，不得将其写成现有能力。

## Evidence Labels

每项关键结论必须采用以下格式：

```text
claim: <结论>
execution: automatic | scripted | manual | convention | absent
evidence: competition-verified | run-evidenced | file-evidenced | document-only | user-confirmed | unknown
sources:
  - <文件路径、Git 提交、命令记录或结果文件>
confidence: high | medium | low
notes: <限制、冲突或无法验证的部分>
```

执行方式定义：

- `automatic`：程序无需人工逐步操作即可完成。
- `scripted`：有脚本辅助，但仍需人工启动、选择或判断。
- `manual`：主要依赖用户命令、对话或手工维护文件。
- `convention`：只依赖文档、目录、命名或团队习惯。
- `absent`：当前不存在该能力。

证据强度定义：

- `competition-verified`：比赛任务、原始结果或完整迭代链能证明实际使用并产生有效结果。
- `run-evidenced`：有运行输出、日志或测试结果证明。
- `file-evidenced`：存在可执行源码、脚本或数据，但没有运行证据。
- `document-only`：只有说明、注释、TODO 或设计文本。
- `user-confirmed`：用户明确确认，但仓库中暂未找到独立证据。
- `unknown`：无法确认。

证据优先级：原始测试结果和迭代记录 > 可执行源码/脚本 > Git 历史 > 同期文档 > 后补说明 > 文件名推断。

## Information To Collect

### 1. 仓库与环境基线

收集：

- 仓库路径、当前分支、commit、工作区状态。
- 排除依赖、缓存和构建产物后的目录树。
- 关键目录的职责、写入者、读取者和真实用途。
- Codex 版本、编译器、驱动、运行时、关键依赖和硬件型号。
- 哪些文件是比赛期间形成的原始材料，哪些是赛后补写或整理的材料。
- 哪些外部环境、硬件状态和历史条件无法安全复现。

### 2. 真实端到端优化流程

至少选择两条真实任务：

- 一条最终取得有效性能提升的完整链路。
- 一条 Gate 未通过、被放弃或发生回退的完整链路。

按真实时间顺序还原：

```text
任务输入
  -> 用户启动 Codex
  -> 提供目标、约束和文件指引
  -> Codex 读取约束与经验
  -> 修改代码并形成待测版本
  -> 清理环境并确认设备可用
  -> 串行执行测试
  -> 生成 benchmark / tracer / profiler
  -> Gate 判断
  -> 继续、采用、放弃或回退
  -> 写回迭代记录和经验
```

每一步记录：执行者、命令或文件、工作目录、输入、输出、前置条件、完成条件、是否需要人工判断、外部依赖、副作用和证据来源。

不要事后重写一个理想流程。原始材料不完整时，保留缺口。

### 3. Codex 的实际使用方式

收集：

- 比赛期间实际使用的 Codex 版本；无法确认则标记 `unknown`。
- 新建对话和 `codex resume` 的真实命令、参数及工作目录。
- Codex 登录态、模型和配置来自哪些路径或键名；不得复制秘密值。
- 初始提示如何编写，任务目标和约束通过什么方式交给 Codex。
- 是否使用 `AGENTS.md`、项目说明、经验索引或其他入口文件。
- Codex 实际读取了哪些文件，而不只是理论上可以读取哪些文件。
- Codex 实际调用过哪些命令和项目脚本。
- 测试结果通过什么方式进入 Codex 上下文：执行脚本、读取文件、用户粘贴或其他方式。
- 对话中断和恢复前后，哪些上下文被保留，哪些需要用户重新说明。
- 是否存在 Thread/Session 标识、JSON 输出、结构化事件、stdout/stderr 约定和稳定退出码。
- 登录缺失、命令失败、进程退出和恢复失败时的可观察信号。

将“Codex 命令及会话行为”和“算子优化领域步骤”分开记录，避免接收方将整个流程锁死在 Codex 上。

### 4. 测试串行化、设备独占与环境清理

还原真实测试顺序：

```text
选择待测版本
  -> 确认设备可用
  -> 防止其他任务占用设备
  -> 清理残留进程、缓存和临时环境
  -> 检查清理结果
  -> 构建或准备测试输入
  -> 只启动一个测试
  -> 等待完成并收集结果
  -> 测试后清理
  -> 再处理下一个版本
```

收集：

- 每个脚本和命令的路径、工作目录、参数、环境变量、依赖、输出和退出码。
- 哪些步骤由脚本完成，哪些只靠用户纪律。
- 如何避免两个测试同时使用同一设备；没有程序锁时明确写 `manual`。
- 清理哪些进程、编译缓存、模型/算子缓存、设备状态、临时文件和环境变量。
- 如何确认设备可用、清理完成、构建成功、测试开始、超时、崩溃和完成。
- 预热、正式采样、重复次数、统计口径、基线校验、误差范围和异常值处理。
- 测试失败后真实采用重试、跳过、放弃还是人工判断。
- 是否支持取消；若没有，写 `absent`。

### 5. Benchmark、Tracer、Profiler 与测试服务

收集：

- benchmark、tracer、profiler 的实际入口脚本或命令。
- 每项工具的输入、输出、文件格式、触发条件、完成判断和错误表现。
- tracer/profiler 是每轮执行，还是由性能异常或 Gate 触发。
- 测试请求如何表达算子、硬件、dtype、shape、代码版本、构建参数和采样配置。
- 真实请求和响应样例；认证字段值替换为 `<redacted>`。
- 远端测试服务在旧项目中的真实职责，必须以代码或契约为依据。
- 服务返回哪些 benchmark、tracer、profiler 数据和执行元数据。
- Agent 推理、知识维护、Gate 或候选处理是否曾出现在远端；存在则明确报告，不要迎合预期边界。

同时按真实证据说明以下动作目前分别对应什么命令、文件或人工步骤；不存在则写 `absent`：

```text
提交测试 / 查询状态 / 读取结果 / 取消测试
获得设备使用权 / 清理环境 / 构建 / benchmark / tracer / profiler
```

### 6. Gate、候选与 current best

定位所有 Gate 相关文档、脚本和结果，收集：

- Gate 名称、适用范围、输入指标、阈值、容差和输出状态。
- Gate 是脚本计算、Codex 判断还是用户人工判断。
- Gate 结果保存在哪里，是否机器可读。
- Gate 如何影响继续迭代、保留候选、更新 current best、触发 profiler、放弃或回退。
- 至少一个 Gate 通过和一个未通过的真实样例。
- current best 如何定义，如何避免未验证结果覆盖它。
- 是否真实存在以下分类；没有证据时不得补造：
  - 通过 Gate，可以成为有效候选。
  - 未通过 Gate，但保留为弱参考。
  - 完全失败，不进入候选集，但保留失败记录或负向经验。
- 完全失败的版本、日志和经验实际如何保留或清理。

### 7. 约束文档

对每份真实约束文档收集：

- 路径、用途、适用硬件/算子/阶段和创建时间或 Git 历史。
- 启动时主动告知 Codex，还是依赖 Codex 自行发现。
- 与其他文档冲突时实际采用哪条规则。
- 哪些规则有迭代记录证明被遵守并产生作用。
- 哪些规则只有文档，没有使用证据。

至少找出三条真实影响过 Codex 行为或优化结果的约束；不足三条时按实际数量报告。

### 8. 经验与知识资产

收集：

- 经验、失败记录、硬件准则和结果总结的路径与格式。
- 是否按硬件平台/型号、算子、dtype、shape、软件栈版本或优化技术组织。
- 用户或 Codex 如何查询、选择和引用相关经验。
- 一条经验如何从某次迭代产生，能否追溯到代码、测试数据和 Gate。
- 是否存在验证状态、去重、合并、冲突、过期、禁用和更新机制；不存在写 `absent`。
- 至少三条真实正向经验的来源、适用条件、使用证据、效果和限制；不足三条时按实际数量报告。
- 至少一条失败经验或反例，以及它是否避免了重复尝试。

仅有简短结论、缺少适用条件或测试证据的经验，必须标记为“不足以直接复用”。

### 9. 迭代历史、版本和回退

收集：

- 版本如何命名、保存和区分。
- 是否使用 Git commit、branch、tag、worktree、patch 或普通目录副本。
- 代码版本如何关联参数、测试结果、Gate、Codex 对话和经验。
- 哪些关联机器可读，哪些只依赖文件名、目录或用户记忆。
- 失败版本如何标记和从有效候选中排除。
- 放弃、回退和验证回退结果的真实命令与步骤。
- 是否存在自动恢复；没有则写 `absent`。
- 至少一条真实 lineage：基线 -> 多次修改 -> 测试 -> Gate -> 失败/回退 -> 最终版本。

### 10. 人工介入

只采集真实行为，不设计审批系统：

- 用户通常在什么信号下介入。
- 介入前查看哪些代码、Diff、指标、日志、tracer 或 profiler 信息。
- 用户通过 Codex 对话给出什么类型的意见。
- Codex 如何根据意见改变方向、修改代码、重新测试或回退。
- 至少提供三个真实片段：纠正错误、补充约束、要求转向/放弃/回退。
- 哪些判断实际上由 Gate 完成，哪些场景确实依赖用户判断。

允许执行：

- 文件和源码搜索。

- 已有离线单元测试。
